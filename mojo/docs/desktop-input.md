# Desktop input boundary

This checkpoint ports the actual desktop caller projection around the verified router. It does not activate routing in the Mojo Window, Timeline or KeyboardController. The application still uses its existing source-tested planners until the complete event/context adapter is connected.

The actual Rust workspace calls the extracted `zz_client::desktop_input` helpers. The original desktop keymap constructor calls `desktop_router`, which clones configured state and removes bindings for the three UI zoom actions from the router. The configured map remains available to prefix fallback. The Mojo `desktop_router_map` keeps these two complete maps separate, with distinct caller-supplied scopes.

The extracted guard preserves the original window/modifier early return, free-drag Escape precedence, and pending dialog-prefix cancellation guard. The projection emits only an active-pane change or detach when the actual active surface changes, applies modal capture except while an overlay is open, and preserves the platform/function/overlay prefix guards. Key releases use existing claims first, without projecting a new active surface or capture. The global desktop caller does not emit the general router's sidebar/editor/overlay focus events.

# Prefix snapshots and queries

`prefix_bindings` retains the actual first table named `prefix`, including binding order, duplicate keys, notes, command source spans, command blocks, alias-group markers, raw arguments and stdin. Full replacements select the first prefix table. A patch removes every matching table name and sequentially replaces the first same-name table in the source; the observable prefix projection therefore uses the last incoming prefix replacement. Hash-only notifications preserve existing bindings. Active-table state keeps the source's `None`/repeat normalization. A validated legacy Hello can supply its typed tables through `reset_connection`; modern Welcome resets the projection before subscribed table events arrive.

The actual Rust desktop queries were moved intact from its mux module into `zz_client::prefix_binding`, and the original module reexports them. The Mojo resolver follows `KeyTables::resolve_input`: one non-control typed scalar first, then the canonical key name, then `Any`. This deliberately includes the source's empty-name/wildcard behavior for platform keys. Duplicate canonical binding keys use the last binding. The all-keys query uses actual command catalog resolution and the exact single `-N` argument. Sidebar-picker recognition preserves the exact `choose-tree` name, exclusive session/window flags, allowed `-s`/`-w`/`-Z` clusters and absence of positionals.

Admission is explicit: 16 MiB encoded frame or retained spelling/raw-data budget, 256 supplied tables or removals, 4,096 bindings and commands, 16,384 argument/block entries, and 64 KiB text fields. Raw argument and stdin bytes share the aggregate budget. Oversize replacements refuse before changing the projection or its generation. The limits are adapter policy; they do not truncate source-valid snapshots.

# Transactions and delivery

`InputRouterSession.prepare_batch` checks at most 32 operations against one unchanged session generation. Every operation still runs the independent typed reducer and, when eligible, the native checked worker. A malformed, foreign or semantically wrong reply falls back to the typed result for that operation's unchanged pre-state. The staged receipt owns the final state, ordered drained delivery and every bounded operation answer; it also captures the original complete state/delivery, source scope and map version. Map or payload replacement invalidates it. Final state and delivery limits are checked before commit. Committing swaps the prepared storage and advances generation once.

`ActionQueue.stage` applies its existing ordering and geometry coalescing to a bounded replacement queue. Append, coalescing, take and batch commit invalidate earlier receipts. Count and aggregate byte limits remain 4,096 actions and 4 MiB. Stage failure leaves the real queue unchanged, including when a multi-action suffix exceeds capacity. Counter exhaustion refuses new admission; take cannot wrap its generation.

`desktop_router_delivery` restricts this more general transaction API to the actual desktop event surface and one physical key per transaction. Public `prepare_key` derives armed/claimed state from the retained `InputRoutingState`, connection presence and actual caller projection. It checks prefix-table/routing coherence, canonical immutable key bytes and all four complete resolver lookups. `commit_key` also compares the captured routing state before committing. That fingerprint admits the 21 source option identities and at most 64 KiB per option/table string; it stays below 2 MiB. Raw active/capture/overlay/Fn/connection properties remain explicit caller metadata from validated app state. The early window/modifier/drag/dialog guard remains a separate caller step. `prepare_events` admits only the actual pane-removal, detach and window-deactivation observer events. The lower-level operation path is internal `_prepare`.

The delivery plan exposes the physical key's exact `native` answer. A swallowed repeat or local release remains Consumed even when both effect queues are empty; callers must not infer propagation from queue lengths. The adapter requires drained effect boundaries, complete matching router/configured maps, matching source identity, and acknowledgement of the previous delivery. It captures both map identities and the prefix generation. It validates the router and action receipts before a callback-free commit using storage swaps. Forwarded immutable key frames become passive native actions with the exact destination pane and `text_follows=false`; the queued frame does not select another pane. Invalid raw payload metadata, a partial lookup list, or a well-typed action from the wrong key refuses the whole plan.

Held ownership follows the actual returned held vector and its actual new Forward effects. A forwarded press or capture repeat refreshes the captured source/epoch/output owner. A swallowed armed repeat preserves it. Releases use the original retained envelope, even after current selection changes. Removed claims retire their envelopes. The desktop sidecar admits source-reachable unique held identities; synthetic duplicate-identity initial states remain supported only by the general kernel boundary. Its map/payload lifecycle methods also require acknowledgement of pending UI delivery, preserve held envelopes, and reuse the same monotonic router session.

Chrome, which-key, sidebar-picker and prefix-chrome results remain bounded typed UI intents behind a one-shot acknowledgement. Which-key retains its immutable actual prefix bindings and optional canonical spelling; prefix intents also retain the original destination pane. Later prefix replacement cannot alter that delivery data. Request-focus and unsupported global Chrome actions are source no-ops. The configured map, rather than the zoom-filtered router map, resolves prefix fallback. The application integration must materialize complete UI/command effects against captured context before consuming those intents; this checkpoint does not claim that the which-key UI or prefix-cancel transport is already connected.

# Checks

Run `python3 mojo/scripts/desktop_input_vectors.py` for the actual-source guard, projection, constructor and retained-prefix comparison. The oracle calls the extracted helpers and the real `ClientCore`, `KeyTables` and command parser; it does not implement a second expected reducer. Full encoded retained bindings are compared as well as query results.

Run `python3 mojo/scripts/desktop_delivery.py` for typed/native transaction, held-owner, source, stale-plan, near-capacity and queue refusal checks. It also substitutes an in-scope, structurally valid but semantically wrong native reply and checks unchanged-prestate fallback. Both wrappers acquire the shared 4 GiB single-job guard. The underlying Bend laws remain those of the pure router and transaction equations; these finite source comparisons and application resource/lifecycle checks add no universal frontend proof claim.

The source comparison passes 8,448 guard cases, 12,288 projections, 13,824 actual desktop-constructor key decisions and 271,872 prefix queries across 118 actual `ClientCore` updates. It compares 832,442 source-result bytes. Cases include every modifier/action combination in the corpus, all three profiles, zoom overrides in multiple tables, duplicate/unsorted tables, duplicate canonical keys, platform wildcards, aliases, option clusters, raw non-UTF8 arguments/stdin, NUL, command blocks, source spans, full/patch/hash/activation updates and Welcome reset. The source/probe build peaked at 521 MiB; the comparison took about 0.18 seconds.

Typed, native, semantically-wrong-worker and missing-worker delivery phases all pass. The native phase executes 47 checked operations plus three deliberate outer-limit fallbacks; complete phases take about 0.15 seconds with roughly 21 MiB maximum RSS. The final authenticated delivery build peaked at 614 MiB. Checks include acceptance at 4,096 final held entries, whole-transaction refusal when a later operation has no capacity, stale receipt after draining delivery, source/map/payload/prefix/queue/routing guards, geometry coalescing invalidation, capture-repeat refresh and captured release epochs, retained which-key data, malformed trailing raw-frame rejection, forged complete/partial lookups, and zero-effect Native/Consumed answers. Existing ActionQueue tests pass. The full underlying 122-trace/21,116-operation comparison, ten worker fault modes, aggregate normal proof and independent verdict pass again; that complete build/check peaked at 1,627 MiB. The aggregate remains 71 public laws and 229 supporting lemmas across 43 modules.
