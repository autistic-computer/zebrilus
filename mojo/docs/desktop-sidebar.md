# Desktop sidebar controller

The desktop sidebar is four Mojo modules, each checked against the Rust code the desktop runs:

- `desktop_host.mojo`: `HostState` (the eight connection states with their attempt, reason and protocol fields), its label, install offer and failure text, the row indicator, and the activation a host row produces (attach to a connected other host, reconnect a failed one).
- `desktop_fleet.mojo`: `FleetModel`, the retained host list. Each host keeps its id, name, state, platform, whether a snapshot has loaded, and the sessions projected from that snapshot with their presentation: session label and index, window name and index, pane heading, folder, kind, provider, bell, status and detected program. It folds the active target across hosts and answers every per-node question the sidebar asks: expandable, pending bell, owner session, renameable name, activation, rename activation and the nine window shortcuts.
- `desktop_nav_tree.mojo`: the structural projection and `SidebarTreeState` (expansion, selection, pointer provenance, active-follow, navigation, focus).
- `desktop_sidebar.mojo`: `DesktopSidebar`, the controller the app shell renders, plus `stage_navigation` and `commit_navigation`.

## Source

The Rust side lives in `zz_client::desktop_fleet` and `zz_client::desktop_host`; `crates/zz/src/mux/nav.rs` delegates `MuxTreeModel`'s expandable, owner, rename, bell and activation queries to them, so the desktop and the vectors run the same functions. Pane rows are headed like the pane header (`window_summary::pane_heading`): a terminal reads its detected program's name, else the last component of its first process entry, else the shell the daemon names in `PaneSummary.shell`, else its label; other kinds read their label, and an agent titled "agent" or untitled reads its provider ("Claude Code", "Codex"). Session rows read `session_label`: a numbered or empty name takes the most common pane folder, keeping the number as the index.

Order follows the source vectors. No sort or deduplication changes the rows. Queries on a duplicated id answer for the first match in host, session, window and pane order, as the desktop's `find` does. Window shortcuts visit only connected hosts and stop after nine windows.

## Entry point for the app shell

`DesktopSidebar(local_hostname)` owns the program catalog, the fleet model, the tree state, the attached host and session, the attached focused pane and the shortcut overlay flag. `revision` increases on every published change.

- `update(hosts, attached_host, attached_session)` takes one `FleetHostInput` per configured host (id, name, `HostState`, `HostPlatform` from the stream's Welcome, current snapshot or none) and returns the row to scroll to. It builds the whole candidate model first; an unchanged model leaves expansion and selection alone, as the desktop's `reconcile_tree` does, and a changed one runs local-host introduction, active-follow and pruning. Platform changes refresh the rows without a reconcile, because the desktop reads the platform live.
- `row_count()` and `rows(first, count, focused)` give the visible rows for a list range: node, depth, label (the local host shows `local_hostname`), pane kind and provider, program, expandable, expanded, on active path, active, keyboard selected, connected, bell, shortcut position while the overlay is shown, host indicator and platform, rename menu label, install offer and whether the host can be removed.
- `click(node)`, `disclose(node)`, `confirm()`, `rename()`, `toggle(node)`, `navigate(direction)`, `focus()` and `window_shortcut(position)` follow the desktop's row click, disclosure click, Enter, rename menu, expand toggle, arrow keys, sidebar focus and Mod+1..9. `new_session(capabilities, working_directory)`, `new_window()`, `split(axis)` and `detach()` follow the app shell's global handlers on the attached host; the working directory is used only for an empty local host, as `MuxClient::new_session` does.
- `node_action(node, action, capabilities, working_directory)` follows a row's hover buttons: 0 new session on a host row (the working directory rule above, for that host), 1 new window on a session row, 2 delete on a session, window or pane row (`kill-session`, `kill-window`, `kill-pane`). Any other pairing is refused; a row on a host that is not connected gives no activation, as the desktop disables those buttons. The activation runs on the row's host, so `stage_navigation` returns `host_request` for a host other than the attached one.
- `chrome_intent(dispatch, capabilities, working_directory)` maps a `DesktopChromeDispatch` (new session, new window, select window 1 to 9, split right or down, detach) to those intents and returns none for the dispatches the shell keeps (sidebar toggle, settings, palette). Call `update` first, as the desktop synchronizes its tree before opening a window shortcut.
- Each returns a `DesktopNavIntent`: the activation, whether the sidebar gives focus back (`release_focus`, a click's means dismissing the slideover), whether the workspace focuses the active pane (`focus_pane`, window shortcuts) and a scroll row.

`stage_navigation(queue, activation, attached_host, source)` turns an activation for the attached host into one staged `ActionBatch`: a session attach is an Attach frame (passive kind 10), and `attach-session -t` targets and executed commands are command requests (kind 16) that the backend sends on the interactive connection. Activations for another host, `AttachHost`, `AttachThenExecute` and `Reconnect` stage nothing and come back as `host_request`; the Mojo backend holds one daemon connection, so the shell has to refuse or route them. `commit_navigation` commits the batch only for the same `DesktopNavSource` (scope, server, client, epoch) and an unchanged queue generation, so a retired source or a queue that moved since staging is refused with nothing published.

## In the workspace

`WorkspaceView` keeps one `DesktopSidebar` and draws it in place of the old session list, window buttons and pane buttons:

- After each poll, `sync_sidebar` calls `update` with one `FleetHostInput` for the local daemon: id 0, the local host name, the current `MuxSnapshot` once one has loaded, the Welcome platform the backend keeps from the connection, and a `HostState` read from the backend: connected while online, unreachable with the last error once a connection failed, connecting otherwise. It skips the call while none of these changed.
- The left panel draws `rows(first, count, False)` with mjui's palette tree row: indent 12 per depth, a disclosure for expandable rows, active and keyboard-selected rows highlighted, a dot for bells and hosts still connecting, the host state for failed hosts and the shortcut position while the overlay is on. A row click calls `click`, a disclosure click `disclose`. The wheel over the panel scrolls it a row at a time, and the scroll row `update` returns is kept in view.
- Every intent goes through `apply_nav`: `stage_navigation` against the backend queue with `DesktopNavSource(connection epoch, server, client, focus epoch)`, then `commit_navigation` with the source read again. The actions carry the current focus epoch, so the backend does not restore the local selection over them; the daemon's view comes back with the next refresh. A `host_request` shows a notice, since this client holds one daemon connection. `release_focus` and `focus_pane` give focus back to the terminal.
- The toolbar's New session, New window, Split right and Split down buttons map to `chrome_intent` with dispatches 1, 2, 4 and 5. The backend no longer has its own session and split actions.
- Keys: `route_workspace_key` resolves the configured map's `ui` table (`desktop_router_map` over `DesktopKeyConfig.map`, so the user's overrides apply) after the palette and before search, unless the window captures input. Dispatches 1 to 6 go through `chrome_intent` (Ctrl+1..9 or Cmd+1..9 select windows across sessions), 7 toggles the panel and 8 shows a notice that settings are not available yet. The key's text and command are claimed and its release is swallowed; a repeat of a held key runs its action again, as the router resolves every press. A window that goes inactive forgets the held keys. This follows the router's order for presses, which reads the `ui` table before forwarding a claimed prefix key; the rest of the router (held keys, `sidebar` and `terminal` tables, prefix chrome keys) is not live yet.
- A split makes a picker pane. A picker pane draws "New pane" with its choices (Terminal, and Browser in a browser build); a click, `t` (or `b`), `j`/`k`/Up/Down and Enter run `select-pane-kind -t %pane <kind>`, Escape runs `kill-pane -t %pane`, as `crates/zz/src/pane/picker.rs` does. Keys with Control, Alt or Command go on as usual, and so does a press the prefix claims (any key while the prefix is armed or a key table is active) or one made while the window captures input: the router forwards those before the picker sees them. The selection kept per picker pane is dropped once the pane is no longer a picker.

`python3 mojo/scripts/sidebar_workspace.py` (pixi task `sidebar-workspace-smoke`) runs this against a private daemon with sessions alpha (windows first and second) and beta (window third): the host row and the session rows in source order, Ctrl+1, Ctrl+2 and Ctrl+3 selecting first, second and third across both sessions with no key state left behind, clicks on the alpha and first rows, New window, Split right with the picker drawn and `t` turning it into a terminal, Split down with the prefix key arming the prefix table on the picker and Escape cancelling it while the picker stays, then Escape closing the picker, and New session. It writes `target/port/sidebar-workspace.png`.

Agent attention badges, the host context menu's install and remove actions, the row hover buttons, the flat chat-mode list, the slideover, sidebar keyboard focus with the `sidebar` table and the shortcut overlay stay with the shell.

## Limits

Admission allows at most 65,536 fleet nodes (hosts, sessions, windows and panes) and 16 MiB of accounted bytes (128 per node plus names, failure reasons, labels and folders), 64 KiB of failure reason per host, and only defined host state and platform tags; a state carrying fields of another state, or a distro on a platform other than Linux, is refused. The tree keeps its own 65,536-node and 16 MiB limits and at most 65,536 expanded or prior-host entries. Every refusal raises before anything is published: model, tree, attached host and revision stay as they were. These limits belong to the port; the source collections are unbounded.

## Checks

- `python3 mojo/scripts/desktop_fleet_vectors.py` encodes 320 generated fleets as protocol snapshots, runs `desktop_fleet` in Rust and the Mojo probe on the same frames, and compares the output bytes exactly: host presentation, sessions, windows and pane headings, the active target, per-node queries with activation and rename command frames, window shortcuts and their activations, and two projected row sets. Its probe also admits a 65,536-node fleet and refuses one more node, an oversized name, an undefined state, foreign state fields, an undefined platform and a distro on macOS; 255 hosts with 64 KiB failure reasons fit the byte budget and a 256th is refused.
- `python3 mojo/scripts/desktop_nav_tree_vectors.py` compares 96 fleets under 1,152 expansion patterns: 3,960 target queries, 10,674 visible rows and 84,780 navigation results in 738,593 bytes.
- `python3 mojo/scripts/desktop_sidebar_vectors.py` compares 64 traces with 6,144 state transitions in 161,314 bytes, then builds all 65,536 visible rows and checks that one node more and an oversized name leave the selection and projection unchanged.
- `python3 mojo/scripts/desktop_sidebar_controller.py` drives the controller over a three-host fleet with exact rows, activations, rename, shortcuts, row actions, global commands and staged batches, including a retired source and a stale queue generation. It then admits a fleet of exactly 65,536 rows and checks that one node more, an undefined host state and a 16 MiB host name leave the rows and revision unchanged.
