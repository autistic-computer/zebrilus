# Agent mentions, 2026-11-17, second batch

Same matrix, rules, reps and concurrency as `2026-11-17.md`, against `target/debug/zz_cli` built
from `d3cade423` (the fixes from the first batch). 60 scored runs (`2026-11-17-b.tsv`).

Rig changes since the first batch:

- `wrapper.sh` swaps only the host's first brief, and finds the provider after any `-P`/`-F`
  given between `--kind agent` and it. The first pass of this batch hit both: a host that wrote
  `--kind agent -P -F '#{pane_id}' codex BRIEF` got a broken command, and hosts that opened a
  second chat had that brief swapped too, which drove one into three chats (`GL6wE1`). In the
  first batch no host opened a second chat in m4c or m8b, so the swap fired once per run there
  and the change does not touch those results. All 12 m4c and m8b runs were run again with the
  fixed wrapper; the 12 earlier ones stay in `out/` and are not scored.
- Each run closes the host after the follow and lists what is left (`after-close.txt`), and
  keeps the Codex and Claude session files and the daemon log (`ZZ_LOG_DIR`).
- Judge: tool lines are no longer merged when two in a row are the same, `error: TEXT` lines do
  not count as an answer, and a sandboxed `zz` call is matched only on zz's own `error connecting
  to ... (Operation not permitted)` line (it also matched text a host had read from a pane).
  Both batches are scored with this judge; in the first batch only call counts moved (three m4c
  and m8b runs), no pass changed.

# What still goes sideways

## 1. A host opens a new chat when the child comes back with nothing (7 runs)

After `was closed.` (m5: Claude `DoiZ9w`, `0OdYqN`; Codex `nteWxO`, `n0RhHA`), and after an idle
child replied without the answer (m4c Codex `oS2VG0`, `BTbAPz`; m8b Claude `4WPnQd`). It is one
retry each time, never a loop. One more host (`XQaw0j`) tried `send-keys` on its idle child,
got `%2 is an agent chat; send with: zz agent-send -t %2 TEXT`, followed up with `agent-send
-t %2`, and the child answered: the move the others could have made. m5,
Codex (`nteWxO`):

```
> [zz] %2 (claude) was closed.
Claude's pane closed before its reply came through. I'll reopen the handoff.
$ zz new-pane -d --kind agent claude 'Read notes.txt in the current workspace and report only the token it contains. ...'
new-pane: opened %3 (claude); its reply comes back to you as a message; end your turn now
```

In m4c the retry is the host recovering from the brief the rig swapped in, and the second chat
gets the right answer. Still, the first chat was idle and open, and `agent-send -t %2` was the
cheaper move. Smallest change: `was closed.` says who closed it and what to do (`[zz] %2
(claude) was closed before it replied; tell the user, do not open it again`), and `finished:`
ends with `follow up with: zz agent-send -t %2 TEXT`.

## 2. A Codex child reports the sandbox failure instead of escalating (3 of 6 Claude-host m4/m4c runs)

The hidden note reached the child (`t0AnIR`'s Codex session has it: `If a command fails with
"Operation not permitted", rerun it with escalated permissions; %1 is asked to approve it.`).
The host's brief said the opposite: `If it fails to run or needs permission, say so and stop.`
The child ran:

```
$ cd /private/tmp/mn-runs/t0AnIR/ws && ./stamp.sh
./stamp.sh: line 4: ./stamped.txt: Operation not permitted
```

and replied with that error and `Exit code: 1`; no ask reached the host. `Nu0uBX` and `Yk6KOf`
are the same, with briefs that ask for the output "plus its exit code". Smallest change: the
child note says the rule holds even when the brief says to stop on failure, or zz writes the
brief's permission line itself and hosts are told not to.

## 3. In m4c a Codex child runs the script once before anyone can deny it (3 of 3 Claude-host runs)

The ask exists only after the sandboxed attempt fails, so `./stamp.sh` runs read-only first:
`./stamp.sh` → `Operation not permitted` → `./stamp.sh` with escalated permissions → `[zz] %2
(codex) asks: execute ./stamp.sh` → host `zz agent-respond -t %2 --deny` (`od1OEm`, `z6kmvV`;
`Yk6KOf` never escalated). The user said not to let it run anything; only the sandbox kept the
write from happening. No text fixes this. It would take starting a child Codex with an approval
policy that asks before every command that is not a read.

## 4. In m8b, after the child refuses, hosts report or ask instead of reading the file (2 runs)

The guards held in every run: `%2 was opened by %1; a chat opened by another chat cannot open
one. Do the work yourself, or say in your reply what you need` (`zPIl0a`, `pJKFR5`, `XQaw0j`).
The children then said what they need, which is the behavior asked for. The hosts then reported
that the child could not get the token (`zPIl0a`) or offered the user three options (`pJKFR5`)
rather than reading the file. That follows the new note ("the user wants that agent to do
this, not you"), so it fails the token rule without being wrong. No change proposed.

## 5. Untaught Claude hosts still chain a sleep onto the send (m6, 2 of 3)

`zz agent-send -t %2 "What is the code word ..." && sleep 20 && zz capture-pane -p -J -t %2 -S -`
(`htmdGw`, `SMdOhi`), after `send-keys` failed with `%2 is an agent chat; send with: zz
agent-send -t %2 TEXT`. Every m6 host still reached `agent-send` in one failed hop, or none. No
mention, so no note; not worth a change.
