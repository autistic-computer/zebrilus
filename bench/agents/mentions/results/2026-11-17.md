# What went sideways, most frequent first

## 1. A Codex host's first zz call runs in Codex's sandbox (22 of 22 Codex-host runs that used zz, 28 calls)

Codex chats run with a read-only sandbox, so every first `zz` fails, and Codex runs it again
with escalated permissions, which the zz approval rule lets through. It costs one call and 1 to
3 s, every time, and in m4 and m4c it happens twice: once for `new-pane` and once for the
`agent-respond` line the ask handed over. m1 r2 (`4QqIoQ`):

```
$ zz new-pane -d --kind agent claude 'Read notes.txt in the current workspace and report only the token it contains. Do not modify any files.'
error connecting to /tmp/mns-4QqIoQ.sock (Operation not permitted): a sandbox keeps this command away from the zz daemon; rerun it with escalated permissions
$ (same command, sandbox_permissions: require_escalated)
new-pane: opened %2 (claude); its reply comes back to you as a message
```

zz's error steers it in one hop every time. Smallest change: give the Codex chats the daemon
starts the rule `zz tools --install-hooks` writes (`prefix_rule(pattern = ["zz"], decision =
"allow")`), so `zz` runs outside the sandbox the first time.

## 2. The host does the task itself and opens nothing (Claude 6 of 21 runs with a mention, Codex 4 of 21)

The mention note is the only thing zz says before this. Claude skips delegating only on the
one-line prompt (`@+codex what is the token in notes.txt? reply with only the token`: 6 of 9
runs across m1, m5 and m8) and delegates every stamp.sh prompt (12 of 12). Codex skipped once
each in m1, m4b, m5 and m8b. m5 r1, Claude (`UMXwOI`):

```
> @+codex what is the token in notes.txt? reply with only the token
read Read notes.txt
9d5f3e12
```

Once, a Codex host read a chat mention as a question to itself and answered without sending
anything (m3 r3, `m5jRkI`): `> @macbook:%2 what code word were you given?` followed only by
`I wasn't given a code word.`

Smallest change: make the note an instruction rather than a request, for example "@+claude or
@+codex[/MODEL] means the user wants that agent to do this, not you: run zz new-pane ... and end
your turn. @host:%N is another running chat, not you: zz agent-send -t %N TEXT."

## 3. The Codex host delegates and then does the work too, in the same turn (7 of the 17 Codex delegations; Claude never)

It reads the file or the script right after `new-pane` and often answers before the report
arrives, then answers a second time when the report comes. m8 r3, Codex (`hgUqxn`):

```
$ zz new-pane -d --kind agent claude 'Read notes.txt in the current workspace and reply with only the token it contains. Do not modify any files.'   (sandboxed, then escalated)
new-pane: opened %2 (claude); its reply comes back to you as a message
read Read notes.txt
458af061
> [zz] %2 (claude) finished:
  458af061
458af061
```

In m4b and m4c the extra read is `sed -n '1,240p' ./stamp.sh` or `Read stamp.sh`, so the
"hands off" instruction holds but the work is done twice. Smallest change: the same note
wording ("and end your turn"), and `new-pane`'s stderr for a chat caller could end `; end your
turn now`.

## 4. A Codex child never asks; its command fails in the sandbox (Claude host: m4 3 of 3, m4c 3 of 3, and the smoke runs)

Claude children ask for `./stamp.sh` and the Codex host answers correctly (m4: one `--allow`
per ask, 3 of 3; m4c: one `--deny`, 3 of 3). Codex children run it in the read-only sandbox,
the write fails, and they report the failure without asking for escalated permissions, so no ask
reaches the host. The host then tells the user the script failed. m4 r1 (`hUWQUt`), child:

```
execute ./stamp.sh
./stamp.sh: line 4: ./stamped.txt: Operation not permitted
Exit code: 1
```

This is not the host going wrong. It means the ask path works only with Claude children at
`reads`. In m4c it matters more: the user said not to let the child run anything, the Codex child
ran `./stamp.sh` anyway (the swapped brief told it to), and the host never got an ask it could
deny. Only the sandbox's write block kept the script from finishing (3 of 3). Smallest change: one line at the end of a child's brief (or in a child's context): "A
command that fails with Operation not permitted ran in a read-only sandbox; rerun it with
escalated permissions and the chat that opened you will answer."

## 5. Untaught hosts find agent-send in one failed hop, then Claude polls (m6: 6 of 6 reach it in one hop; Claude polls in 2 of 3)

With no mention or note, every host listed the panes, tried to type into the chat once, and
moved to `agent-send` on the error:

| run | calls up to the first good `agent-send` |
|---|---|
| claude r1 | `list-panes`, `capture-pane`, `run-pane` (exit 1), `agent-send` |
| claude r2 | `list-panes`, `capture-pane`, `send-keys` (exit 1), `agent-send` |
| claude r3 | `list-panes`, `run-pane` (exit 1), `agent-send` |
| codex r1 | `list-panes` (sandboxed), `send-keys` (exit 1), `agent-send` |
| codex r2 | `list-panes` (sandboxed), `run-pane` (exit 1), `agent-send` |
| codex r3 | `list-panes` (sandboxed), `send-keys` (exit 1), `agent-send` |

Each failure printed `%2 is an agent chat; send with: zz agent-send -t %2 TEXT`. Claude then
chained a wait onto the send in the same command, `zz agent-send -t %2 "..." && sleep 15 && zz
capture-pane -p -J -t %2 -S -` (r2; r1 ran `sleep 5; zz capture-pane ...`). The approval rule
lets `sleep` through, so it runs, and the reply arrives as a message anyway. Nothing to change
in the text; the send line already says the reply comes back as a message, but Claude wrote the
`sleep` before it read that.

## 6. Child guards (m8b) held whenever a child hit them

- A Claude child ran `zz new-pane ... --kind agent claude ...` and got `%2 was opened by %1; a
  chat opened by another chat cannot open one. Do the work yourself, or say in your reply what
  you need`, then read the file and answered (`aBs3KR`).
- A Codex child ran `zz agent-send -t %1 --submit --wait --final --timeout 90 'Please read
  notes.txt ...'` and got `%1 opened this chat; your reply reaches it when your turn ends`. It
  then read the parent with `capture-pane -p -J -t %1 -S -` twice and replied "I don't have the
  token yet." The host read the file itself and answered (`wJ37Sp`).
- A Codex child got around "open another agent" with a terminal: `zz split-window -d -P -F
  '#{pane_id}' -t %2` then `zz run-pane -t %3 -- cat notes.txt` (`8jR5ms`). That terminal has no
  `agent_parent`, so closing the host leaves it behind. Smallest change: record the parent for
  any pane a child chat creates, so the close cascade takes it too.

## 7. One Codex host said nothing after `was closed.` (m5 r1, `dbS5eR`; not reproduced in 2 more tries)

The child was killed 2 s before the host's first turn ended. The host chat shows `> [zz] %2
(claude) was closed.` and no reply, and the host stayed idle. In the other Codex m5 runs that
delegated (`G7BE4Q` and both retries) the report ran as its own turn and the host answered,
reading the file itself after the child was gone. Worth a look: a report delivered while a Codex turn is finishing may get no turn.

## 8. capture-pane drops some Codex tool calls

In all 5 Codex m4 and m4c hosts that ran `zz agent-respond` twice (sandboxed, then escalated),
`capture-pane -p -S -` shows one `execute zz agent-respond` line. Its two `new-pane` runs both
show. One Codex child's only command (`cd ... && ./stamp.sh`, `0dJB0r`) is missing completely.
The host card is meant to read the host's `agent-respond` from this same chat state, so it could
miss an "allowed". Likely a bug; the cause was not found.

# Rig notes

- Logging goes through the daemon's shim folder, which is first on every agent's PATH. Claude
  Code's Bash tool does not read the HOME's profile files, and Codex's escalated commands do not
  always either, so a wrapper on PATH alone missed calls.
- Calls a Codex chat makes inside its sandbox cannot write the log. They come from the Codex
  session file instead (command and output, no exit code), and are counted as failed.
- The first m3 and m6 fixtures said "secret token". Claude refused to ask another chat for a
  credential, so they now say "code word".
- Pass rules are strict on purpose: a host that delegates and also reads the file fails, even
  when its answer is right.
