# What was compared

Rex is Superlogical's multiplexer: a Go server embedding Ghostty, a SwiftUI app, and a `rex`
CLI. The build on 2026-10-15 reported `0.0.1792088193-g7a93ec` (the app updates itself). zz is
main at e2a93d5c7, `target/release/zz_cli`; tmux is 3.8 from Homebrew. Machine: M4 Max, 16
cores, macOS 27. Both harnesses run Rex as `rex server run` on a private socket with an empty
config and never touch the user's own Rex server.

# Server cost (`bench/perf`, group `rex`)

Raw JSON: `bench/perf/results/rex-macbook-e2a93d5c-20261015T214029Z.json`. Medians.

| metric | zz | tmux | Rex |
|---|---|---|---|
| one-shot `list sessions`, wall | 3.9 ms | 5.3 ms | 16.0 ms |
| server CPU per `send` | 0.14 ms | 0.13 ms | 3.7 ms |
| footprint, 1 pane / 20 panes | 4.8 / 11.1 MiB | 2.8 / 2.9 MiB | 21.2 / 35.5 MiB |
| threads, 20 panes | 5 | 1 | 36 |
| footprint, 20 panes after `seq 1 12000` | 19.1 MiB | 61.4 MiB | 62.2 MiB |
| idle wakeups, 20 panes | 0/s | 0/s | 14/s |
| new window, wall | 5.8 ms | 7.5 ms | 34.4 ms |
| detached `cat` 150 MiB ASCII / unicode | 293 / 115 MB/s | 42 / 9 MB/s | 293 / 121 MB/s |
| 10 panes at 100 lines/s, server CPU | 1.2% | 2.3% | 5.5% |
| attached `cat` 150 MiB ASCII | 541 ms | 4323 ms | 1607 ms |
| bytes the TUI received for it | 0.2 MB | 7.1 MB | 161 MB |
| TUI client CPU for it | 5 ms | not sampled | 874 ms |
| same flood, TUI never reads: time / server peak RSS | 0.5 s / 33 MiB | 4.2 s / 171 MiB | 10.5 s / 115 MiB |

Rex keeps all 12000 lines of history where zz and tmux keep about 10000, so its scroll row
carries a fifth more history. The tmux client CPU reads 0 in every group; the probe does not
see it.

What the numbers say:

- Parsing is a tie. Both servers drive libghostty and both beat the blocking-read pty ceiling
  (218 MB/s) the same way; Rex is 5% ahead on unicode, which is the one place zz has headroom
  (the July notes put zz's unicode path at `vt_write`).
- Rex pays for Go: 4x the memory at rest, 36 threads, 14 wakeups a second with nothing
  running, 4x the CLI latency and 25x the server CPU per CLI call.
- The client models differ. `rex attach` passes one block's bytes straight through (it binds
  the session's first block and does not follow focus), so a flood costs the client every byte
  and, when the client stalls, Rex slows the program down instead of dropping frames. zz sends
  conflated frames: 0.2 MB for 150 MiB, and a stalled client never slows the program. tmux
  buffers 171 MiB and slows the program. For phones and ssh links the zz model is the right one.

# Agent usage (`bench/agents/skill`)

Raw rows: `bench/agents/skill/results/2026-10-15-zz-vs-rex.tsv` (348 runs). Same fixture and
prompts on both backends, eleven shared tasks plus t8 (zz agent pane). Haiku 5.5 through
`claude -p` once per cell, gpt-oss-120b through `agy -p` twice per cell.

Haiku passes everything on both (zz 66/66, Rex 43/44), so it measures cost. On the shared
tasks a Rex run takes a median of 167k input tokens, 6 CLI calls and 14 s; a zz run 96k, 3
calls and 11 s. Agents reach for `--help`, JSON output and full block ids on Rex; on zz they
already know the tmux verbs.

gpt-oss decides the delivery question (shared tasks, n=22 per cell):

| arm | zz | Rex |
|---|---|---|
| none | 14 | 15 |
| skill as shipped (zz: full SKILL.md; Rex: stub) | 15 | 16 |
| stub pointing at `zz tools --skill` | 16 | - |
| startup hook + shipped skill | 18 | 9 |
| startup hook + stub | 19 | - |
| guide inline in the prompt | 21 | 17 |

- The inline guide wins for weak models, as in September. A SessionStart-style hook gets most
  of the way for about 1 KB: zz hook arms 18-19/22 against 14-15 without one. For Haiku the
  hook is also the cheapest arm: 96k tokens and $0.032 for twelve tasks, against 142k and
  $0.045 with the full skill file and 175k with the stub alone.
- A stub alone costs tokens (the agent runs `zz tools --skill` and reads 13.6 KB); behind a
  hook it costs nothing extra, because agents rarely open the guide.
- Rex's own hook hurts: 9/22. It tells the agent to rename the session before anything else;
  gpt-oss spent its turns on `rex session rename` with bad flag orders, reused the hook's
  example label `fix-login-redirect`, and named windows through block labels. Keep a hook to
  facts about where the agent is and how to target things.
- Both products fail t11 (find the pane waiting for a yes/no answer, 1-2/3 in most arms) and
  t12 without targeting rules (act on the focused pane, 1/3 for none and skill). The zz hook's
  here/focused/named rules lifted t12 to 2-3/3. Neither product gives agents a cheap "which pane
  is waiting" answer for programs that do not report status.
- t10 (one failing test in 3000 lines): agents on both products pull the whole history and
  filter it with `grep` in their own shell, so tokens stay low (zz 126-187k, Rex 165-308k for
  Haiku) even though zz's CLI printed more bytes. Bounded output flags would not change much.

# What to do

1. Ship a startup-context hook for Claude Code and Codex, opt-in, generated by the zz binary,
   and pair it with a stub skill so the guide follows the installed version. Built the same day:
   `zz tools --context`, `zz tools --install-hooks` / `--remove-hooks`, and the context sent
   directly to Claude and Codex agent panes (see the agent-pane follow-up below).
2. Keep the hook to location and targeting; no tasks for the agent to do first.
3. Look at a "waiting for input" signal for plain terminal programs (t11), using the screen and
   the foreground process, with the provenance kept separate from program-reported status.
4. Nothing to borrow from Rex's server or client for performance; the unicode path is the only
   row where it leads.

# After building it (same day)

zz now gives agents the context three ways: `zz tools --context` (answered by the local CLI, empty
outside zz), `zz tools --install-hooks` / `--remove-hooks` for Claude Code and Codex started by hand
in a terminal pane (a guarded SessionStart hook plus a stub `zz-workspace` skill), and the daemon
passes the same text to Claude agent panes (`--append-system-prompt`) and Codex agent panes
(`developerInstructions` after the user's own `developer_instructions`, read with `config/read`).
`ZZ_AGENT_CONTEXT=1` on agent children keeps an installed hook from repeating it.

Rerun with the shipped text, Codex `gpt-6-luna` once per cell and Haiku on the hook arms (rows in
`bench/agents/skill/results/2026-10-15-luna-haiku-shipped-hook.tsv`):

| arm | zz luna | Rex luna | zz luna median input tokens |
|---|---|---|---|
| none | 11/12 | 11/11 | 41k |
| skill | 11/12 | 11/11 | 66k |
| inline | 11/12 | 11/11 | 52k |
| stub | 12/12 | - | 90k |
| hook (shipped text) | 12/12 | 9/11 | 50k |
| hook + stub | 12/12 | - | 82k |

Haiku with the shipped hook: 12/12 in both hook arms at 96k tokens. Luna only fails t11 on zz,
and only without the hook: it ran `list-panes`, which in tmux lists the current window, never saw
the `deploy` window, and answered the wrong pane. With the hook it followed `list-panes -s` and
found it. Rex's `block ls` lists the whole session by default, so Rex passes t11 unaided, and its
own hook again cost two tasks. Luna spends about half the input tokens on zz that it spends on Rex.
